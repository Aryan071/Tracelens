# Architecture Decision Records

## ADR-0001: Monorepo with Docker-based toolchains
- **Status:** accepted
- **Context:** Go services, Node/TS demo and VS Code extension share one schema and one compose stack. Host has no Go and Node 14.
- **Decision:** Single repo (`/ingest /engine /indexer /api /extension /demo /docs /bench /schema`). Builds, codegen and tests run in pinned Docker images via `make`; host needs only docker + make. npm workspaces for JS.
- **Rejected:** per-service repos (schema drift, no atomic cross-cutting changes); host-installed toolchains (non-reproducible, CI/host divergence); pnpm (extra dependency, no benefit at this size).

## ADR-0002: JSON Schema is the source of truth for Evidence
- **Status:** accepted
- **Decision:** `schema/evidence.v1.schema.json` (2020-12) owns the contract. Python (Pydantic v2) models via `datamodel-code-generator` (originally Go via `go-jsonschema`; see ADR-0004), TS types via `json-schema-to-typescript`; CI fails if regenerated output differs from committed (`make gen-check`). Items are a `oneOf` discriminated by `type`; IDs are deterministic (`ev_...`), never random, so golden files are stable and LLM citations are verifiable.
- **Rejected:** Go structs as source (makes TS second-class); protobuf (poor fit for LLM-facing JSON and golden files).

## ADR-0003: Go-side typed decoding and range validation are hand-written
- **Status:** superseded by ADR-0004 (Go removed)
- **Context:** go-jsonschema (a) maps `oneOf` to `interface{}` and (b) enforces only `required`, not min/max/pattern. A test caught `confidence: 1.5` being accepted.
- **Decision:** `engine/pkg/evidence/items.go` dispatches on `type` into generated structs with strict (no unknown fields) decoding, and `validate()` checks ranges. `TestAllSchemaTypesHandled` fails if the schema gains a type the decoder lacks.
- **Consequence:** range rules are duplicated by hand and can drift (patterns such as SHA and trace-ID format are not yet enforced in Go). 
- **Proposed fix:** adopt a real JSON Schema validator in Go (e.g. `santhosh-tekuri/jsonschema`) and run all examples through it. Needs approval as a new dependency.

## ADR-0004: Python for backend services (supersedes Go choice and ADR-0003)
- **Status:** accepted (owner decision, 2026-10-03)
- **Context:** The original spec chose Go. The owner chose Python. Phase 0 Go code was small (generated types, decoder, 3 tests) so migrating before Phase 1 is cheap.
- **Decision:** Ingest, indexer, engine and API are Python 3.12, managed as a `uv` workspace (`pyproject.toml` + committed `uv.lock`). Evidence models are generated from the JSON Schema by `datamodel-code-generator` as Pydantic v2 models (`extra="forbid"`, field constraints). Tooling: `ruff` (lint+format), `mypy --strict`, `pytest`. All run in a pinned `uv` Docker image locally (ADR-0001) and via `setup-uv` in CI.
- **Consequences (positive):** Pydantic enforces required fields, ranges, patterns and unknown-field rejection, so the hand-written Go decoder and range checks are deleted. Statistics (Mann-Whitney U) are easier. Previously unenforced constraints (SHA/trace-ID patterns, schema version) are now tested.
- **Consequences (negative / risk):** Ingestion throughput and per-core CPU are lower than Go. Mitigation: async receivers, bounded queue, batched native ClickHouse inserts, `uvloop`, multi-process workers. The Phase 1 benchmark will report the real number; if ingestion cannot meet its target, rewriting only that service is cheap because the schema and storage boundaries are language-neutral.
- **Rejected:** Go (original; kept for reference), TypeScript (single-language but weaker throughput than Go and similar to Python for CPU work), Rust (highest cost for this project size).

## ADR-0005: ClickHouse `spans` table design
- **Status:** accepted
- **Decision:** `MergeTree`, `PARTITION BY toYYYYMMDD(start_time)`, `ORDER BY (service, name, toStartOfHour(start_time), start_time)`, `TTL toDateTime(start_time) + INTERVAL <RETENTION_DAYS> DAY` with `ttl_only_drop_parts = 1`, `non_replicated_deduplication_window = 1000`. Attributes are `Map(LowCardinality(String), String)`; hot attributes (`http_route`, `http_method`, `db_system`, `db_statement`, `code_function`, `code_filepath`, `code_lineno`) are MATERIALIZED columns that coalesce the current semantic-convention name with the legacy one, so the correlation engine never scans the Map. Events are a `Nested` (parallel arrays) so Phase 5 can read exception stack traces. `trace_id` is a `FixedString(32)` hex string with a bloom-filter skip index.
- **Why:** The dominant queries (Phases 3-5) filter by service and endpoint over a time window before/after a deployment, so a service/name-first sort key prunes best and compresses well. Daily partitions make retention a metadata-level part drop (hourly would create too many parts; weekly makes drops coarse).
- **Verified on this server (24.8):** nanosecond `DateTime64(9)` round-trips exactly; `Nested` insert works; legacy `code.function` falls through the materialized column; inserts with the same `insert_deduplication_token` are deduplicated while different tokens are not (so a retry after a lost response cannot duplicate a batch).
- **Consequences:** (1) Fetching all spans of one trace is not served by the sort key; it relies on the day-pruned bloom-filter index. A trace-ordered projection was planned as the alternative but has NOT yet been benchmarked; this is deferred to the Phase 6 query-latency benchmark where the trace-waterfall query actually exists. (2) ClickHouse applies TTL at insert: spans older than the retention window are discarded immediately (found by an integration test, not by reading docs). (3) Changing `RETENTION_DAYS` issues `ALTER ... MODIFY TTL` at startup.
- **Rejected:** `trace_id`-first ordering (hurts the main regression queries); hourly partitions; a separate trace-lookup table (extra write amplification for an unmeasured benefit); `async_insert` (server-side batching would take backpressure out of our hands).

## ADR-0006: Acknowledge after enqueue; reject with a retryable status when full
- **Status:** accepted (owner approved, 2026-10-03)
- **Decision:** Receivers decode, convert and offer the request to a bounded, span-counted, all-or-nothing buffer and acknowledge immediately; they never await ClickHouse. When the buffer is full: HTTP 429 + `Retry-After: 1` / gRPC `RESOURCE_EXHAUSTED`; during shutdown: 503 / `UNAVAILABLE`. A background batcher flushes at 10,000 spans or 1 s and retries failed inserts forever with exponential backoff and the same dedup token. On SIGTERM it stops admitting, drains, and exits non-zero (counting `spans_lost_total`) only if the shutdown deadline (default 30 s) is exceeded.
- **Why:** Meets "never block the receiver on storage". OTLP exporters already retry 429/503/UNAVAILABLE, so overload becomes backpressure, not loss.
- **Consequence:** a hard crash can lose acknowledged-but-unflushed spans (bounded by the buffer size). Mitigation, if needed later: an on-disk write-ahead log. Not built, to avoid unmeasured complexity.
- **Rejected:** ack after insert (durable, but couples receiver latency and availability to ClickHouse); unbounded queue (memory blow-up); silently dropping when full (data loss).
- **Also decided:** all-or-nothing admission per request (no OTLP partial success) so retry semantics are trivial; spans with all-zero or wrong-length ids are invalid per OTLP, are dropped and counted (`spans_invalid_total`); OTLP/HTTP supports protobuf only (OTLP/JSON not implemented; returns 415).

## ADR-0007: `clickhouse-connect` as the ClickHouse client
- **Status:** accepted
- **Decision:** `clickhouse-connect` (HTTP, maintained by ClickHouse), column-oriented inserts from one client per worker thread.
- **Measured cost:** about 93k spans/s per core for encoding + insert on this payload (LowCardinality dictionaries and Map encoding dominate).
- **Rejected:** `clickhouse-driver` (native protocol, potentially faster, but community-maintained with a weaker async story). Not benchmarked head to head; revisit only if the client becomes the limiting stage again.

## ADR-0008: Scale ingest with processes (`SO_REUSEPORT`), not threads
- **Status:** accepted
- **Context:** Profiling showed the single process pinned at one core: conversion and ClickHouse encoding each cost about a core at roughly 100k spans/s, so the GIL caps one process near 24k spans/s end to end.
- **Decision:** `INGEST_PROCESSES=N`: a supervisor runs migrations once, spawns N workers sharing the OTLP ports via `SO_REUSEPORT` (each with its own buffer, split from `BUFFER_MAX_SPANS`, and batcher), and serves aggregated Prometheus metrics (multiprocess mode). If any worker dies unexpectedly, the supervisor stops all so the orchestrator restarts the service. Result: about 24k to about 81k spans/s (HTTP) on 4 processes.
- **Weakness found by measurement:** the kernel hashes connections to workers with no load awareness, so a few long-lived connections can skew onto one worker (one gRPC run reached only 46k vs 69k). Options if this bites: more connections per client, or a small front-door that round-robins. Not implemented.
- **Rejected:** threads / free-threaded Python (not yet a safe default with C-extension dependencies here); sub-interpreters; rewriting conversion in a native extension (deferred: would need new dependencies and only removes one of two roughly equal costs).

## ADR-0009: Content-addressed parse cache; commits are manifests
- **Status:** accepted
- **Context:** The indexer must support incremental re-indexing per commit and, in Phase 4, symbol-level diffs between two deployed SHAs.
- **Decision:** Parsed facts (symbols, imports, exports, calls, routes, SQL literals, type bindings) are keyed by git **blob SHA** and parsed once ever. A commit is a manifest `path -> blob_sha` (`commit_files`) built from `git ls-tree`; a commit becomes queryable only when its manifest, edges and routes are published in a single transaction. Paths stay repo-relative so they equal OpenTelemetry `code.file.path` values; `scope` restricts indexing to a path prefix (e.g. `demo`). Each symbol stores a `body_hash` of its comment-free leaf tokens, so Phase 4 can diff symbols between commits without re-parsing, and formatting-only edits are not changes. `PARSER_VERSION` invalidates the cache when extraction changes.
- **Measured:** the 3,270-file move/rename commit parsed 2 blobs; unchanged commit parses 0.
- **Rejected:** per-commit full re-parse (O(repo) per commit); storing symbols per (commit, path) (duplicates identical content across thousands of commits); using file mtime/`git diff` as the only change signal (does not handle reverts, branches, or renames for free).
- **Consequence:** the same content parsed at two paths with different extensions shares one parse (language chosen from the first path). Accepted.

## ADR-0010: Memoized, commit-independent call-edge resolution
- **Status:** accepted
- **Decision:** A file's call edges depend on its own blob and on what its imports resolve to. They are memoized on `(caller blob, caller path, deps_hash)` where `deps_hash` hashes each import's specifier -> resolved path -> blob, plus the blobs of every file in the re-export closure of the targets (barrel files), and records unresolved specifiers as such (so adding a missing file invalidates the memo). Edges are stored once, keyed by that triple, and a commit sees an edge only if the caller file's `deps_hash` equals the one the commit computed and both endpoints are present at the recorded paths. A change re-resolves the changed file and exactly the files whose dependency hash changed.
- **Verified:** `test_incremental_index_equals_from_scratch_index_after_every_commit` indexes a sequence of 9 edits (leaf edit, barrel change, deleted import target, dropped base class, router mounted twice, module rename, revert) incrementally and from scratch after each, and requires identical symbols, edges, routes and SQL. Tests also assert exact re-resolution counts (e.g. a change behind a barrel re-resolves the file, its direct importer and the barrel's importer, and nothing else).
- **Rejected:** recomputing every edge per commit (O(repo)); invalidating by "any file changed" (defeats incrementality); name-based global fallback for unknown receivers (makes a file's edges depend on unrelated files, so it cannot be memoized, and it adds wrong edges).
- **Known cost:** a change to a widely-imported module re-resolves all importers (measured: ~1,400 files, 1.4 s).

## ADR-0011: Resolution without a type checker (explicit heuristics, measured)
- **Status:** accepted
- **Decision:** Calls resolve only through statically visible facts: lexical scope, imports/re-exports (relative paths and the TS `.js`->`.ts` convention; **no tsconfig path aliases**), `this`, one inheritance level, `super`, and *declared or constructed class types* (`x: Foo`, `x = new Foo()`, `constructor(private x: Foo)`). Everything else is counted as unresolved and never guessed. `this.a.b()` is resolved only when `a` has a visible class type and is never mistaken for `this.b()`. Each edge carries a resolution kind and confidence.
- **Measured against the TypeScript checker on typeorm `src`:** 100% precision (0 wrong of 7,375 verifiable), 75.8% recall. Misses require type inference.
- **Rejected:** shipping a TypeScript language service (large dependency, slow, needs `node_modules`, not available for other languages); matching unknown receivers by method name (wrong edges would pollute critical-path attribution in Phase 3).
- **Honest scope:** evaluated on one codebase. JavaScript-heavy or functional codebases may have lower recall.

## ADR-0012: Positions from byte offsets; never call `Node.start_point`/`end_point`
- **Status:** accepted
- **Context:** The first benchmark run died with a segfault on real code. Bisecting showed `py-tree-sitter` 0.26.0 crashes in `Node.start_point`/`end_point` under sustained use (7 of 8 runs of a loop that calls only those two properties; zero crashes without them), while parsing and all other node accessors were stable.
- **Decision:** Line and column are derived from byte offsets with a precomputed newline table (`bisect`); the Point API is never used. Columns are byte columns, as in tree-sitter. A regression test parses repeatedly in a child process so a reintroduction fails an assertion instead of killing the test runner; the crash was re-verified fixed by parsing all 3,611 typeorm files in one process.
- **Consequence:** pinned to `tree-sitter` 0.26 by the lockfile; revisit when upgrading.

## ADR-0013: Route extraction rules (Express/Fastify)
- **Status:** accepted
- **Decision:** A call is a route registration only if its receiver is plausibly a router: the result of a known factory (`express()`, `express.Router()`, `Fastify()`, `new Router()`), a variable typed `Express`/`Router`/`FastifyInstance`, the first parameter of an inline `register(async (instance) => ...)` plugin, or a conventionally named variable (`app`, `router`, `fastify`, `server`, `api`, `instance`; confidence 0.6 unless the framework import is also present). Inline handlers become synthetic `route_handler` symbols named `METHOD /path` at their real file and line, and calls inside them are attributed to that symbol. Mounts (`app.use('/p', router)`, `register(plugin, {prefix})`) are composed across files into full paths; a router mounted twice yields two routes; cycles terminate. Non-literal paths are recorded as dynamic (`<dynamic>`), never guessed. Decorator routing (NestJS) is not extracted.
- **Found by review:** the first golden contained a false route (`ctl.get(req, res)` in an Express file was parsed as `GET <dynamic>`); the receiver check above fixes it, with a regression test.
- **Query semantics (owner-approved):** "which symbol handles POST /orders" returns the registered handler (a synthetic symbol for inline handlers) plus its direct callees, so the caller sees both the handler and the functions it delegates to. `:id` and `{id}` match each other.

## ADR-0014: Span trees are repaired, never rejected; local self-time vs global critical time
- **Status:** accepted
- **Context:** Real demo traces show children ending after their parents (pg.query ends up to 0.6 ms after the traced() span that issued it; a cross-service SERVER span ends 0.2 ms after its CLIENT parent), handlers whose spans end long before their async work finishes, and spans arriving without parents. Naive `duration - sum(children)` goes negative.
- **Decision:** `build_forest` never raises: orphans become roots, duplicate span ids keep the first by (start, end, name), self-parents and parent cycles are broken by promoting the earliest member, and every repair is counted (`Forest.issues`) and surfaced as a warning on profiles. Output is independent of input order. **Self time** is local and exclusive: `duration - |union of children clipped to the span|` (union so parallel children are not subtracted twice; clipping so an outliving child cannot drive it negative). A child that starts at or after its parent's end is **detached** (fire-and-forget / consumer): it subtracts nothing and is reported as an async tail, never charged to the parent.
- **Rejected:** dropping spans that violate nesting (loses real data); subtracting raw child durations (negative self times); treating detached children as part of the parent's wait (the parent did not wait).

## ADR-0015: Critical path = last-finishing child, clamped; unmapped time rolls up to the nearest mapped ancestor
- **Status:** accepted (owner approved the roll-up and detached-child policies, 2026-10-03)
- **Decision:** Walking back from a span's end, the child that finishes last before the cursor is what the span waited for; time between that child's end and the cursor is the span's own critical time; recurse, continue from the child's start. Children overlapping the critical child are not on the path. Child windows are clamped to the parent's window, so exactly one span owns every instant and **sum(critical) == root duration**, which is asserted on thousands of random trees (and holds on live data to 0.04%). Iterative, O(k log k) per node, no recursion limit (a 20,000-deep chain is tested). Per-endpoint aggregation charges each critical slice to the **nearest mapped ancestor-or-self symbol** (mapping confidence >= 0.5), keeps the spans it flowed through as `via`, and reports leftover time as an explicit `<unmapped>` bucket with a warning above 20%. The aggregation unit is the subtree under a matching SERVER span, so inner-service endpoints profile the same way and cross-service work is attributed to the remote functions.
- **Rejected:** attributing only to leaf spans (framework/DB spans have no symbol, so regressions could not be localized to code); including detached work in the critical path (the root did not wait); reporting unmapped spans separately without roll-up (less useful for locating regressions; the spans are still visible in `via`).

## ADR-0016: Trace-to-code mapping: three tiers with explicit confidence
- **Status:** accepted
- **Decision:** (a) `semconv` 0.99, up to 1.0 with a matching line; legacy attribute names are accepted because ClickHouse materializes the coalesced `code_function`/`code_filepath`/`code_lineno` columns at insert (tested end to end); paths match by longest suffix (absolute, relative and Windows paths work; a bare filename is weaker, x0.85); `Class.method`, bare, `Object.`/`async`/`exports.` forms resolve; ambiguity lists candidates and lowers confidence. (b) route: SERVER and Express `request handler` spans, `http.route` + method (`:id`/`{id}` equivalent) to the handler symbol, 0.95, 0.7 when parsed from the span name, x0.65 for a suffix match, x0.9 when a route shared by several services is disambiguated by the service name, multiplied by the extractor's own route confidence. (c) fuzzy span name, INTERNAL spans only, token (Dice) similarity >= 0.6, **hard-capped at 0.6** so it can never outrank a deterministic tier. Framework spans and boundary spans (CLIENT/PRODUCER/CONSUMER) deliberately stay unmapped. Results are deterministic regardless of symbol load order (found by a test: tie-breaking used insertion order).
- **Known limits:** compiled paths (`dist/orders.js`) do not match `.ts` sources until Phase 5's source-map support (they fall back to a unique-name match at 0.6); no line numbers are emitted by the demo.

## ADR-0017: Regression detection design (rank test + controls + effect-size gates)
- **Status:** accepted (owner approved hand-rolled statistics and control normalization, 2026-10-04)
- **Context:** On this laptop, identical code shows run-to-run p50 swings of about 28% when other work competes for CPU (17.1-17.4 ms vs 21.9-22.3 ms across consecutive windows), while p95 wanders between 20 and 28 ms. A rank test with a p-value cutoff would flag a no-op redeploy: at hundreds of samples such a shift is overwhelmingly "significant".
- **Decision:** Requests are grouped by the SERVER span's `service_version` (not by time). The new version's first `warmup_s` seconds are dropped. Fewer than 30 requests on either side is `insufficient_data` and is never flagged. **Control endpoints** are endpoints with a known (non-empty) critical path containing none of the symbols changed between the two commits; the median of their p50 ratios (the smallest ratio when fewer than three controls exist) is divided out of every "after" sample, a multiplicative model of environmental effects. Tests are one-sided Mann-Whitney U ("after is slower"), tie- and continuity-corrected, all in one Benjamini-Hochberg family per comparison. A flag also requires BH-adjusted p < 0.01, common-language effect >= 0.6, a relative p50 or p95 increase >= 10% and an absolute increase >= 1 ms. Statuses: regression / improvement / environmental / ok / insufficient_data; identical commits can never be a code regression.
- **Statistics are hand-rolled** (about 60 lines) and validated against scipy 1.18.1 on 182 Mann-Whitney and 30 Benjamini-Hochberg reference vectors (heavy ties, zero-inflated, tiny and unbalanced samples), agreeing to 1e-9. scipy generated the vectors offline in a throwaway container and is not a project dependency. One deliberate divergence: with every observation tied scipy returns NaN for the two-sided p; we define "no information" as p = 1.
- **Found by tests:** an endpoint with no mapped symbols was counted as a control (vacuously "unchanged") and normalized its own improvement away; controls now need a known critical path. A 15% relative-delta gate left power at 88% for a true +20% shift at n=100 (percentile estimates are noisy at that size); at 10% it exceeds 90%.
- **Amendment (found by the end-to-end run):** normalization may suppress a flag but never create one. A fixed wall-clock cost (a busy-wait) does not speed up when the machine does, so dividing by an environment factor below 1 made an endpoint look slower than its controls while its raw latency fell 12%. A regression must now also be confirmed in the raw, un-normalized data (common-language effect >= 0.55 and a raw p50 or p95 increase of at least half the relative-delta gate); otherwise the endpoint is `ok` with a note. Cost: a small true slowdown hidden under a large machine-wide speedup can be missed.
- **Calibration (BENCHMARKS.md):** overall A/A false-positive rate 0.83%, but about 2% at n=40 and 0-0.3% at n=250; power 96% for +20% at n=100.
- **Known limits:** the multiplicative model assumes environmental effects scale latency; a regression in code shared by every endpoint is partly absorbed by the controls (the output warns when no usable control exists, and one contaminated control is outvoted when three or more exist); if a downstream service also changed version the result carries a confounder note. The window comparison is across time, so time-of-day effects are not modeled.
- **Rejected:** a plain test with a stricter effect-size floor (cannot separate environment from code, would flag the noise above); scipy as a dependency (heavy for ~60 lines that can be verified against it); comparing only against a fixed latency threshold (no notion of an endpoint's own baseline).

## ADR-0018: Commit ranking by symbol-level overlap, with stated limits
- **Status:** accepted
- **Decision:** For each commit between the two deployed SHAs (first-parent diff for merges) every changed source file is parsed at both sides with the Phase 2 extractor and symbols are compared by qualified name using the comment-free token hash: formatting-only and comment-only edits are not changes (verified on real commits). Added, removed and modified symbols are scored against the regressed symbols weighted by each symbol's share of the latency increase (full credit for modified/added, 0.3 for removed, 0.35 for a direct caller or callee because an un-spanned helper's time is charged to the function that called it), capped at 1.0 per commit. A container's hash covers its members, so editing a method also marks its class modified; this is intended (a regressed function that encloses an edited closure still overlaps). Non-source changes (SQL, config) are listed and never scored (Phase 5). Output: ranked commits with reasons.
- **Honest limit:** two commits that change the same hot symbol are statically indistinguishable. They receive the same score and name each other in `ambiguous_with`; the documented tie-break is newest first. Renamed or moved symbols appear as removed + added.
- **Rejected:** ranking by diff size or recency (no connection to the regression); running a bisect (needs deploying every commit; out of scope).

## ADR-0019: Deployments, the API service and the schema bump
- **Status:** accepted
- **Decision:** `deployments(service, version, commit_sha, repo, deployed_at)` in PostgreSQL (migration 003 in the shared metadata migration sequence), unique per (service, version); re-registering the same mapping is idempotent (200), a different commit for an existing version is 409, the database also enforces the SHA format. Versions seen in telemetry but never registered are discovered from ClickHouse at query time and shown as unmapped: regressions can be detected for them, commits cannot be ranked. The API is a FastAPI service (`api/`) whose OpenAPI document is committed (`api/openapi.json`) and checked for drift in tests and `make gen-check`. Evidence schema 1.0.0 -> **1.1.0**, additive: `route_name` mapping method; optional control-normalization, effect-size, commit-ambiguity and critical-time fields; every 1.0.0 document remains valid (tested in Python and TypeScript). The API runs the metadata migrations at startup.
- **Rejected:** requiring registration before any analysis (blocks first use); storing observed versions (derivable, would go stale).

## ADR-0020: Scripted bad deployments live in a scratch clone
- **Status:** accepted
- **Decision:** Scenarios are exact-string source edits (`demo/bad-deployments/scenarios.py`, an anchor that is not found exactly once is an error) applied as real commits in a scratch clone, mixed with decoys: a whitespace-only edit, a comment-only edit, unrelated new functions, and edits to functions off the critical path. Deployments are built from `git archive <rev>`, so the container runs exactly the committed tree, labeled with `service.version`. The sync-call scenario busy-waits 25 ms on the event loop in the `createOrder` hot path; the N+1 scenario issues one extra query per returned order in `findOrdersByUser`. Missing-index and thrown-exception scenarios need SQL and error correlation and arrive in Phase 5.
- **Rejected:** patch files (break on any demo change); committing bad code to this repository's history.

## ADR-0021: SQL fingerprints come from a tokenizer applied to both telemetry and source, at read time
- **Status:** accepted (Phase 5)
- **Context:** Spans carry `db.query.text` / `db.statement` (parameterized by the `pg` driver: `$1`), the indexer stores SQL string literals found in source. To say "this slow query is that line of code" both must reduce to one key.
- **Decision:** `sqlfp.normalize` is a regex tokenizer (strings, E-strings, dollar quotes, quoted identifiers, comments, numbers with sign folding, `$n` / `?` / `%s` / `:name` / `@p` parameters, `::` casts). Output is lowercase, single-spaced, comment-free, every literal and parameter is `?`, `IN (...)`, `ARRAY[...]` and multi-row `VALUES` are collapsed. The fingerprint is the first 16 hex digits of its SHA-256. The same function normalizes span statements and source literals, **at load time**: the index stores raw literal text only, so a change to the normalizer needs no re-index and no migration (the 004 migration from the plan was dropped for this reason).
- **Rejected:** a SQL parser dependency (new dependency, fails on vendor syntax, still needs the literal-stripping step); fingerprinting inside the indexer (couples index validity to normalizer version); semantic normalization (alias renaming, predicate reordering): a missed match is acceptable, a wrong match is not.
- **Known limits:** SQL built at runtime (string concatenation, query builders) has no literal to match and is reported unmapped. A comma-separated `FROM a, b` list names only its first table (ddl.tables_of).

## ADR-0022: SQL regressions are detected on time-per-request per fingerprint
- **Status:** accepted (Phase 5)
- **Decision:** For each regressed endpoint, each fingerprint (at least 10% presence on either side, at most 12 by mean time) is tested on the time per request spent in that query (zero for requests that did not run it), one-sided Mann-Whitney U on the control-normalized "after" series, BH-adjusted over the endpoint's fingerprints, with the same effect-size and absolute-increase gates as the latency detector. That one quantity moves for all three failure shapes, which are labeled for display: `slower` (per-call p50 up at least 20%), `more_calls` (calls per request up at least 1.2x: N+1), `new` (absent before). `calls_before/after` are means over all requests so a new or removed query shows as 0.
- **Rejected:** testing per-call latency only (blind to N+1, the most common ORM regression); a separate environment estimate for SQL (the latency detector's control factor is already the best estimate of machine speed and keeping one number avoids two disagreeing normalizations).
- **Limit:** queries are only examined for endpoints already flagged; a slow query that does not move any endpoint is not reported.

## ADR-0023: A schema migration is tied to a regression through the tables the slow query reads
- **Status:** accepted (Phase 5)
- **Context:** A missing-index regression changes no application symbol, so symbol-overlap ranking (ADR-0018) scores every commit 0. The cause is a `.sql` file.
- **Decision:** For `.sql` files in a commit, the DDL statements added relative to the parent (multiset difference of normalized statements, so reformatting or reordering adds nothing) become events (`drop_index`, `create_index`, `alter_table`, `drop_table`, `create_table`). `DROP INDEX` names no table, so the index-to-table map is built from the `CREATE INDEX ... ON t` statements of the OLD tree. A commit is credited when an event's table is read by a flagged query (tables from `FROM/JOIN/UPDATE/INTO`; an unqualified name matches a qualified one by suffix). Credit = the query's share of the endpoint's latency increase x a factor (drop index 1.0, alter/drop table 0.6, create 0.3), added to symbol credit and capped at 1.0. If EXPLAIN is configured and shows a sequential scan of that table the credit stands; if it shows none the credit is halved and the reason says so.
- **Rejected:** blaming every non-source commit in the range (flags READMEs); scoring by file name (`migrations/`); running the migration to see what changes (side effects).
- **Limits:** name-based, so a table reached through a view, or an index dropped by a script that never created it in the old tree, is missed (reported as unlinked, not guessed). Applying a migration out of band (not in git) is invisible.

## ADR-0024: Error identity is type + normalized message + throwing function; frames resolve through source maps
- **Status:** accepted (Phase 5); resolves open questions 7 and 17
- **Decision:** V8 stacks are parsed (`stacktrace.py`); the first in-application frame (not `node_modules/`, not `node:`, has a file and line) identifies where an error comes from. Source Map v3 is decoded by a 100-line decoder (`sourcemap.py`, validated against a real `tsc` build and a real Node stack) rather than a library. Maps are found under `<--sourcemaps>/<version>/` mirroring the repository layout; a container path matches by longest existing suffix, and the map's relative `sources` resolve to repo-relative TypeScript paths, which is the key of the code index. The resolved line selects the innermost indexed symbol containing it. The fingerprint is `sha256(type | message with numbers, ids and quoted values replaced | file-stem:function)[:16]`: **no line number** (it moves with every edit above the throw) and the file **stem** (so a deployment without maps, `dist/orders.js`, groups with one that has them, `src/orders.ts`). A group is "new in a deployment" if its fingerprint has no occurrence in the previous deployment's events and it occurred at least 3 times. Without maps an unambiguous function name still maps (method `function_name`, lower confidence); an ambiguous one does not.
- **Rejected:** keeping maps inside TraceLens per build artifact upload API (more surface for the MVP; a deploy step copying `dist/*.map` is the same contract); emitting `code.line.number` from the demo (compiled lines are wrong without maps; the decoder makes them unnecessary for errors, and span mapping works from `code.function.name` + path).
- **Limits:** stem collisions between two files of one name in different directories can merge groups; an error thrown from a callback with no in-app frame groups by type and message only; pre-existing errors that got more frequent are a rate question and are not reported as new.

## ADR-0025: EXPLAIN is opt-in, plan-only, single-SELECT, read-only
- **Status:** accepted (Phase 5)
- **Decision:** With `--replica-dsn` / `TRACELENS_REPLICA_DSN` set, each flagged query is planned with `EXPLAIN (FORMAT JSON, GENERIC_PLAN, VERBOSE)` (PostgreSQL 16: parameters stay `$n`, the plan a prepared statement gets). Never `ANALYZE`. Only a single statement whose first keyword is SELECT or WITH is accepted; anything else is refused and noted. The connection is read-only with a 5 s statement timeout, and the transaction is rolled back. The summary names the chain of node types along the costliest path plus scan details, and records which tables are sequentially scanned.
- **Rejected:** planning DML (a bug in the guard would have consequences); `EXPLAIN` with sampled literal values (we only keep normalized text, and it would give a plan for one value); EXPLAIN ANALYZE (executes the statement).
- **Limit:** the replica shows the plan NOW, not the plan that ran during the regression; evidence says so by being a plain summary, and the commit credit is only weakened (not removed) when the plan disagrees.

## ADR-0027: The query API is read-only, one project per process, and serves views of one cached comparison
- **Status:** accepted (Phase 6)
- **Decision:** `GET /endpoints`, `/comparisons`, `/symbols`, `/queries/{fingerprint}`, `/traces/{id}`, `/commits/{sha}`, `/source` (OpenAPI committed in `api/openapi.json`, drift-checked). `/comparisons`, `/symbols` and `/queries` are three views of one engine run (`RegressionRun`), which loads thousands of traces, so `PipelineBackend` caches it per (service, from, to) for 30 s (configurable, 32 entries) under a lock. The backend is configured by environment for a single repository (`TRACELENS_REPO`, `_REPO_NAME`, `_SCOPE`, `_SOURCEMAPS`, `_REPLICA_DSN`); multi-repository is DESIGN.md open question 25. Conversions from engine objects to response models are pure functions (`convert.py`) tested without a database; the routes are tested against a fake backend whose comparison is built by the engine's own analysis of synthetic data, and the git endpoints against a real temporary repository. `/source` rejects absolute paths and `..`, both endpoints validate the sha shape, and a patch is capped at 200 KB. CodeLens latency is the p95 of the time a symbol spends on the critical path, pooled over endpoints and counted only over requests that reach it ("how slow is it when it runs"), compared with the same quantity in the baseline deployment.
- **Rejected:** one endpoint returning everything (the editor would fetch traces and diffs it never shows); computing in the extension (the logic belongs where it is tested with the rest of the engine); a materialized results table (staleness; the 30 s cache is enough for an editor).
- **Limits:** a cache hit can be up to 30 s stale; the first request after a deployment takes as long as the analysis (about 2-3 s on the demo); no authentication (non-goal for the MVP; the compose file publishes the API on localhost only).

## ADR-0028: Extension = pure core + thin VS Code glue, tested at three levels
- **Status:** accepted (Phase 6); dependencies `@types/vscode` and `@vscode/test-electron` approved by the owner
- **Decision:** Everything that is logic lives in `extension/src/core/` and imports nothing from `vscode`: the API types, formatting (the lens text "p95 820ms ↑64% since v2.18.4"), index-path-to-document matching, the tree model, the waterfall geometry, and the webview HTML. The glue (`session.ts`, `tree.ts`, `lens.ts`, `open.ts`, `extension.ts`) is small. Tests: (1) unit tests of the core with `node:test`, including HTML escaping and CSP; (2) a contract test validating the API's golden responses (written by the API's own tests, one file serving both languages) against `api/openapi.json` and the Evidence schema, plus a compile-time check that the same files fit the TypeScript interfaces; (3) tests inside a real VS Code (`@vscode/test-electron`) that exercise the tree, CodeLens, code/commit/query/trace click-through, config switches and API failure against a stub server that serves those golden responses. The editor tests use a 30-line harness instead of mocha (an extra dependency for no capability we use). The trace webview has a nonce-based CSP with `default-src 'none'`, no inline handlers, and everything from the server is HTML-escaped. Links in the page carry `data-*` attributes and a single listener posts typed messages to the host. Commits open as VS Code's own diff editor over a `tracelens-source:` virtual file system backed by `/source`, queries as a virtual SQL document, so navigation, find and theming are VS Code's.
- **Rejected:** a webview framework (non-goal; the page is a list and some bars); generating TypeScript from OpenAPI (a new tool; the contract test plus the compile-time check cover drift); a mocked `vscode` module (tests would assert against our own idea of the API).
- **Limits:** the webview's click handlers are covered by the page's `data-*` contract and the host's message handler, not by a simulated click inside the webview (VS Code offers no API for that); the editor tests need a display (an X server, or `xvfb-run` in CI).

## ADR-0029: The explanation layer: validate, retry once, fall back to a deterministic template
- **Status:** accepted (Phase 7); dependency `anthropic` approved by the owner
- **Decision:** `explainer/` (`tracelens_explain`) takes ONE Evidence document and returns an `Explained` (summary, claims each with citations, `source` llm|template, model, attempts, rejections, fallback reason). The model receives `canonical_json(evidence)` (sorted, compact) and a system prompt, nothing else; on the single retry it also receives the validator's exact complaints. Its answer is accepted only if it (1) parses as the expected JSON, (2) cites at least one ID per claim, (3) cites only IDs that exist in this document, and (4) states no number that is absent from the items it cites (rounding, percent and ms/s changes allowed; SHAs, fingerprints and versions are not measurements). A rejected answer is retried once; a second rejection, a refusal, truncation or any API error ends in the template, which is built from the evidence alone, passes the same validator, and is what the extension shows with the LLM off (`TRACELENS_LLM=off`, or no credentials). `explain` never raises and never returns something that failed validation (tested with scripted models, including garbage, refusals and API errors). The call uses `output_config.format` (JSON schema) so shape errors are rare, the default model is `claude-opus-5-5` (`TRACELENS_LLM_MODEL` overrides), thinking is left at the model's default and `effort` is `medium`.
- **Rejected:** letting the model see source code, traces or prior explanations (the contract is evidence-in, citations-out, so every claim is checkable); free-text answers parsed with regexes (a schema is available); retrying more than once (the second failure is information: the template is better than a third attempt); server-side refusal fallbacks to another model (the template is the fallback, it is deterministic and needs no second model, and a refusal on a diagnosis of a latency regression means something is wrong with the request, not that a different model should be tried); scoring explanations with another LLM (non-deterministic, and the point is a check that does not trust a model).
- **Limits:** the validator cannot judge whether a true claim is the right conclusion (docs/EVAL.md); numbers inside prose that the model rewrites into words ("a quarter") are not checked; a model answer that is valid but unhelpful is accepted. The live-model evaluation has not been run (no credentials in the build environment); only the template and the validator were measured.
- **API and UI:** `POST /explanations` (body: an Evidence document; 413 over 200 KB, 422 if it is not valid Evidence). The trace panel renders the waterfall first and fills the explanation in when it arrives; each citation links to the evidence item in the panel, a citation that is not an item of the document is shown as unresolvable (`[id?]`), the badge says whether a model or the template wrote it, and a failed or slow explanation never blocks the waterfall.

## ADR-0030: Performance of the cold comparison: what the profile showed and the two fixes
- **Status:** accepted (Phase 8)
- **Context:** the first `GET /comparisons` for a selection took about 3.2 s on the demo data (87k spans), shown to the user once per selection while the tree, lenses and views wait for it.
- **Decision:** (1) Row conversion: `loader._span` passes the ClickHouse row positionally into `Span` (the columns are selected in field order and the driver already returns `str`/`int`), and `Span` is a `slots` dataclass that is no longer `frozen=True` (a frozen dataclass assigns each of its 17 fields through `object.__setattr__`: 2.14 us per instance against 0.40 us; `unsafe_hash=True` keeps it hashable; nothing in the code base assigns to a span). (2) Mapping: `map_span` is memoized per `MemorySymbolIndex` on exactly the fields the three tiers read (name, kind, service, code function, file and line, route, method, inherited method), bounded at 20,000 shapes with a clear-on-full policy because some instrumentations put ids in span names. Result: 3.18 s -> 2.5-2.6 s median (about 20%) in three interleaved A/B rounds (BENCHMARKS.md), 546 tests unchanged, new tests pin the row mapping, the hash/equality behavior and that the cache key covers every field the tiers read.
- **Rejected:** loading the six (service, version) groups in parallel threads (the Python conversion and tree work are GIL-bound and the wait on ClickHouse is under half of the fetch stage; not tried, so no number is claimed); caching comparisons longer (staleness for little gain, 30 s already serves everything after the first request); computing self-time and critical path inside ClickHouse SQL (a large change to the most-tested code); `NamedTuple` for spans (as fast to build, but a span would then compare and unpack as a tuple, and the tests use `dataclasses.replace`).
- **Limits:** a memoized mapping assumes the index does not change while it is held, which is how it is used (an index is loaded per comparison); the measured gain is on this data and machine state, and what remains is mostly ClickHouse transfer and decode plus pure-Python tree and timing code.
